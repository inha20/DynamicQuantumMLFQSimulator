## 2. 지표 정의와 모델 가정

코드(`mlfqsim/sim.py`의 `_metrics`)에서 읽은 그대로의 정의다. 이후 문서가 지표를 인용할 때 이 정의를 쓴다.

| 지표 | 정의 | 주의 |
|---|---|---|
| `avg_wait` | task별 대기 합의 평균. 대기 하나는 큐에 들어간 틱부터 디스패치 틱까지다 | 도착 후 첫 대기, 선점이나 quantum 소진 뒤 재대기, I/O에서 깨어난 뒤 대기가 모두 들어간다. 문맥 전환 정지 틱은 대기가 아니라 CPU 오버헤드다 |
| `avg_resp` | 첫 디스패치 틱 - 도착 틱의 평균 | 첫 디스패치 틱에 정지가 있으면 실제 첫 실행은 그보다 늦다 |
| `int_lat_mean`, `int_lat_p95` | interactive task의 모든 대기 구간의 평균과 p95 | 그림 제목의 "wakeup latency"는 정확히는 이 모든 대기 구간이다(깨어난 뒤 대기만이 아니다) |
| p95 | 정렬한 표본의 인덱스 floor(0.95 n) | 표본이 20개 이하이면 최댓값이다(n = 20이면 인덱스 19) |
| `batch_slowdown` | batch task의 (끝 - 도착) / CPU 작업량의 평균 | |
| `max_wait`, `starved` | 대기 구간 하나의 최댓값, 그 값이 `starve_thresh`를 넘은 task 수 | |
| `switches`, `switch_per_kt` | 디스패치한 task가 그 CPU의 직전 task와 다르면 +1. 1000 x 전환 수 / makespan | 같은 task가 같은 CPU에서 이어 실행하면 I/O 뒤에도 전환이 아니다(H3) |
| `migrations` | 마지막으로 실행한 CPU와 다른 CPU에서 디스패치한 횟수 | 첫 실행은 이주가 아니다. 이주하면 그 task의 남은 작업량에 `mig_penalty`가 더해진다(H9) |
| `util` | 원래 작업량 합 / (CPU 수 x makespan) | 이주 페널티로 늘어난 작업은 세지 않는다(유효 이용률) |
| `overhead_frac`, `idle_frac` | 정지 틱 합과 노는 틱 합을 (CPU 수 x makespan)으로 나눔 | |
| `imbalance` | (CPU별 실행 틱의 최대 - 최소) / 최대 | |
| `makespan` | 마지막 task가 끝난 시각 | |
| `jain_batch` | batch 지연 배수 s의 Jain 지수 (합 s)^2 / (n x 합 s^2) | batch가 없으면 1 |

모델이 **가정**하는 것(결함이 아니라 설계이며 시험으로 확인했다):

- global 큐는 실제로 경합하는 CPU가 몇 개인지와 상관없이 디스패치마다 `lock_cost x (CPU 수 - 1)`틱을 CPU별로 누적해 정수 부분만큼 정지한다. 그래서 일 하나뿐이어도 CPU가 많으면 느려진다(H10: lock_cost 1.0일 때 CPU 1, 2, 4개에서 끝 11, 13, 17). README가 "선형 모델"이라고 한 것이 이것이다.
- boost는 대기 시작 시각을 바꾸지 않는다. 그래서 boost 주기 P가 `max_wait`의 정확한 상한이 아니다(H5. E3에서 P=100일 때 `max_wait`는 109.9).
- 선점은 대기 중인 task의 레벨이 실행 중인 task의 레벨보다 엄격히 높을 때만 일어난다(H4, H14).

## 4. 발견 F1: 같은 틱 이중 사용

### 4.1 무엇인가

`mlfqsim/sim.py`의 틱 처리는 CPU를 0번부터 차례로 훑는다. quantum을 다 쓴 task는 `ready_since = t + 1`로 표시되어 **그 틱 안에서 바로** 큐에 들어가므로, 같은 틱 t에 번호가 더 큰 CPU가 그 task를 가져갈 수 있다. 그러면

- 그 디스패치의 대기가 t - (t + 1) = -1로 기록된다.
- 가져간 CPU는 task가 마지막으로 실행한 CPU와 다르므로 이주가 세어지고 이주 페널티가 더해진다. 같은 CPU가 다음 틱에 이어 실행하는 것이 정상이다.
- 가져간 CPU에 정지가 하나도 없으면 같은 task를 두 CPU가 같은 틱에 실행한다. 정지가 없으려면 문맥 전환이 없어야 하는데(그 CPU의 직전 task가 바로 그 task일 때, 또는 `cs_cost`가 0일 때) 락 정지도 없어야 한다.

### 4.2 최소 재현(시험 H8)

일 하나(10틱)를 CPU 2개에서 돌린다(quantum 4, 레벨 1은 8, `lock_cost` 0).

| 모델 | 끝 | 전환 | 이주 | 대기 기록 |
|---|---|---|---|---|
| 기본(`defer_requeue=False`) | 17 | 2 | 2 | `[0, -1, 0]` |
| 보정(`defer_requeue=True`) | 11 | 1 | 0 | `[0, 0]` |
| CPU 1개 | 11 | 1 | 0 | `[0, 0]` |

일 하나는 CPU가 늘어도 빨라지지도 느려지지도 않아야 하는데, 기본 모델에서는 6틱 느려진다. 문맥 전환 비용을 0으로 두면 같은 틱에 두 CPU가 실행하는 경우가 드러나 끝이 15(정상 10)가 된다. 1코어에서는 뒤 순서 CPU가 없어 일어나지 않는다.

### 4.3 얼마나 자주 일어나는가

`results/validation/f1_negative_waits.csv`(seed 0~9, 기본 비용, 기본 모델). 대기가 음수인 디스패치가 F1 사건이다.

| 구성(mixed, static) | 디스패치 | F1 사건 | 비율 | 이주(기본) | 이주(보정) |
|---|---|---|---|---|---|
| 1코어 | 7337 | 0 | 0% | 0 | 0 |
| global 2코어 | 15906 | 50 | 0.31% | 7867 | 7460 |
| global 8코어 | 65067 | 695 | 1.07% | 55440 | 55926 |
| global 16코어 | 145020 | 1716 | 1.18% | 133015 | 128396 |
| per-CPU 8코어(soft, 밸런싱 100, 훔치기) | 57246 | 483 | 0.84% | 6160 | 5775 |
| per-CPU 8코어(strict, 훔치기, 밸런싱 없음) | 57847 | 504 | 0.87% | 1390 | 1004 |

- 이 표는 일부이고 CSV에는 서로 다른 구성 31개가 있다. 그중 4개(1코어, 그리고 훔치기와 밸런싱이 모두 없는 per-CPU 3개)는 F1 사건이 0건이다. 나머지는 전체 디스패치의 0.02~2.0%이고, 가장 높은 것은 8코어 global의 feedback 정책(2.04%)과 batch workload(2.03%)다. starve workload에서는 0.02~0.06%다.
- global 멀티코어 11개 구성에서는 F1 사건이 이주의 0.02~2.4%라 이주 대부분은 F1과 무관하다. per-CPU에서는 비율이 더 높고(0.4~36%), **strict affinity와 idle 훔치기에서는 이주 1390건 중 504건(36%)이 F1 사건**이다. strict는 원래 이주가 거의 없기 때문이다.
- 이 사건 중 정지가 없어 실제로 같은 틱에 두 CPU가 실행한 경우는 16090건 중 194건(1.2%)이다(`zero_stall_events` 열, 기본 비용). global에서는 12건(2코어 10, 4코어 2, 8코어 이상 0)이고 나머지 182건은 per-CPU다. 8코어 이상 global에서는 락 비용 0.25 x (CPU 수 - 1)이 1 이상이라 디스패치마다 락 정지가 1틱 이상이므로 이 경우가 생기지 않는다.
- E1~E6은 모두 `cs_cost=1`이다. 1코어(E1~E3)는 F1의 영향이 없고, E4~E6(멀티코어)이 영향을 받는다.

같은 구성을 두 모델로 돌린 값이다(`results/validation/ci_summary.csv`의 `F1-*` 행과 `E4-*`, `E5-*`, `E6-*`의 `model` 열). 구간은 95% 쌍체 부트스트랩이다.

| 수치(mixed, seed 10개 평균) | 기본 모델 | 보정 모델 | 변화 |
|---|---|---|---|
| E4 global 평균 대기, 2 / 4 / 8 / 16코어 | 2840 / 3459 / 4028 / 5725 | 2813 / 3442 / 4083 / 5554 | -1.0% / -0.5% / +1.4% / -3.0% [-3.7, -2.1] |
| E4 per-CPU 평균 대기, 2 / 4 / 8 / 16코어 | 2139 / 2194 / 2168 / 2157 | 2140 / 2146 / 2146 / 2152 | 0.1% / -2.2% / -1.0% / -0.3% |
| E4 이주(16코어), global / per-CPU | 13302 / 1469 | 12840 / 1368 | -3.5% / -6.9% |
| E5 strict + 훔치기 이주(밸런싱 없음) | 139.0 | 100.4 | -27.8% |
| E5 strict + 훔치기 이주(밸런싱 100) | 187.3 | 148.7 | -20.6% |

| E6 global 평균 대기(락 0, 이주 10) | 10591 | 10285 | -2.9% [-7.4, +2.0] |

두 모델에서 같은 방향으로 나온 비교: E4에서 per-CPU의 평균 대기가 global보다 모든 코어 수에서 낮다(seed 10개 모두), global은 코어가 늘수록 나빠지고(2 -> 16코어에서 +102%와 +97%) per-CPU는 구분되지 않는다(+0.9%와 +0.6%, 구간이 0을 포함). E6에서 락과 이주 비용이 모두 0이면 평균 대기는 구분되지 않고(차이 +14, 구간 -19~+44와 -8~+37) global의 interactive p95가 낮다(0.7 대 12.3과 0.8 대 14.5). 즉 **F1은 수치를 바꾸지만 위 비교들의 방향은 바꾸지 않았다.** 같은 구성을 두 모델로 돌린 20개 구성(`F1-*` 행)에서 바뀐 정도는 평균 대기 최대 3.9%, interactive p95 최대 9.2%, makespan 최대 2.1%, 이주 횟수 최대 20.6%다. 이주 횟수가 가장 크게 바뀐 구성은 strict + 훔치기 + 밸런싱 없음(1390 -> 1004건, -27.8%, `f1_negative_waits.csv`)이다. 이주를 직접 인용하는 문장은 모델을 함께 적어야 한다.

### 4.5 지금의 처리와 사람이 정할 것

- 시뮬레이터에 옵션 `Config.defer_requeue`(기본 `False`)를 더했다. `True`이면 quantum이 끝난 task를 그 틱이 끝난 뒤에 큐에 넣는다. 기본값이 `False`이므로 동작과 저장된 결과는 그대로이며, 재현 점검(§6)이 그것을 확인한다.
- README의 E4~E6 수치는 기본 모델의 값이다. 이 저장소는 결과 파일을 바꾸지 않았다.
- **사람이 정할 일**: 어느 모델을 기본으로 삼고 E4~E6을 다시 낼지. 기본값을 바꾸면 README의 E4~E6 수치가 모두 바뀐다. 확인용 실행 계획(G5 초안)의 열린 항목으로 올린다.

## 5. 불변식과 같은 입력 관계

모두 `tests/test_invariants.py`의 `Invariants`에 있고, 기본 모델과 보정 모델을 나눠 확인한다.

- **시간 보존**: CPU 용량(CPU 수 x makespan) = 원래 작업량 + 이주 횟수 x 페널티 + 정지 틱 + 노는 틱. 작업량은 task 목록에서, 정지와 노는 틱은 CPU별로 따로 세므로 한 틱이 빠지거나 두 번 세어지면 어긋난다. 두 모델 모두 성립한다(5개 workload, 1/2/4/8코어, 4개 정책).
- **범위**: 0 < 이용률 <= 1, 이용률 + 정지 + 노는 비율 <= 1, 0 < jain <= 1, batch 지연 배수 >= 1, 0 <= imbalance <= 1, task마다 (끝 - 도착) >= 작업 + I/O, makespan >= 작업량 합 / CPU 수.
- **task별 시간 항등식**: 비용이 모두 0이면 (끝 - 도착) = (대기 합) + (CPU 작업) + (I/O)가 정확히 성립한다. 대기를 실행 중에 세거나 두 번 세면 어긋난다. 1코어는 기본 모델에서, 멀티코어는 보정 모델에서 성립한다. 비용이 있으면 부등호(>=)로 성립한다.
- **대기가 음수가 아님**: 1코어(기본 모델)와 멀티코어(보정 모델)에서 성립한다. 멀티코어 기본 모델에서는 성립하지 않으며(F1), 이를 expectedFailure로 기록해 두어 고치면 "예상 밖 성공"으로 알려 준다.
- **같은 입력 관계**: CPU 1개에서 global과 per-CPU의 결과가 같고 `defer_requeue`가 영향을 주지 않는다. 일 하나의 끝은 CPU 수와 무관하다(락 비용 0, 보정 모델에서 성립, 기본 모델은 F1으로 성립하지 않아 expectedFailure로 기록).
- **workload 생성기**: task 수(`per_cpu` x CPU 수, starve는 13 x CPU 수), 버스트가 CPU로 시작해 CPU로 끝남, interactive CPU 버스트 1~4틱과 I/O 범위, batch 작업량 400~1200(starve는 600), 도착 패턴(mixed 0~2000, bursty는 세 파동, starve), interactive 비율(0.8, 0.5, 0.5, 0.2의 +-0.05), seed마다 다른 workload.

## 6. 재현 점검

`analysis/check_reproduce.py`는 `experiments.py`를 임시 폴더로 처음부터 다시 돌려(46초) `results/`와 비교한다. CSV 6개와 `results/summary.md`는 줄바꿈(CRLF, LF)만 맞추면 바이트까지 같다. 그림 3장은 그리기 라이브러리 버전에 따라 바이트가 달라 비교하지 않는다. 이 점검은 `Config.defer_requeue`를 더한 뒤의 코드에서 통과했다.

## 7. 변이 점검

`analysis/mutation_check.py`는 시뮬레이터(`mlfqsim/sim.py` 22곳, `policies.py` 11곳, `workload.py` 3곳)를 임시 사본에서 한 곳씩 틀리게 고치고 시뮬레이터 시험(`tests/test_sim.py`, `tests/test_invariants.py`)을 돌린다. 시작할 때 변이를 넣지 않은 사본이 시험을 통과하는지 먼저 확인한다. 틀린 곳의 예: 문맥 전환 비용 무시, 락 비용에 (n-1) 대신 n, 이주 페널티 무시, 같은 레벨도 선점, boost 시각 어긋남, boost가 실행 중인 task를 올리지 않음, soft affinity 경계, 밸런싱 문턱, 훔칠 CPU 선택, I/O 길이, 대기 계산, 유효 이용률 정의, p95 위치, feedback EMA 가중치, hybrid를 곱 대신 합으로, 기본 모델을 보정 모델로 바꾸는 변경. 결과는 `results/validation/mutation_check.csv`이고 변이마다 처음 실패한 시험의 이름이 들어 있다.

36개 모두 시험이 잡았다(약 3분, 시간 초과로 잡힌 것은 없다). 점검을 두 번 고쳤다.

1. 처음 돌렸을 때 "유효 이용률에 이주 페널티 작업량을 포함"하는 변이 1개를 놓쳤다(이주가 있는 사례에서 이용률을 검사하지 않았다). 사례 H9에 이용률과 노는 비율 검사를 더한 뒤 잡힌다.
2. 그 뒤 분석 도구 시험(`tests/test_analysis_tools.py`)을 더했을 때 점검이 `tests/` 전체를 사본에 복사했다. 사본에는 `analysis/`가 없어서 이 시험 파일이 가져오기 오류로 실패했고, 그 때문에 **변이가 무엇이든 '잡힘'으로 나왔다**. 결과 CSV의 '처음 실패한 시험' 열이 36행 모두 같은 파일 이름이어서 알아챘다. 시뮬레이터 시험만 복사하고, 변이를 넣지 않은 사본이 통과하는지 먼저 확인하며, 복사하는 시험이 도구를 가져오지 않는지를 시험으로 지키도록 고친 뒤 다시 돌렸다. 위 36개는 고친 점검의 결과다.

변이는 사람이 고른 36가지이므로 시험이 모든 결함을 잡는다는 뜻이 아니다. 전부 '잡힘'으로 나오는 결과는 점검 자체가 헛도는 경우에도 나오므로, 처음 실패한 시험의 이름이 변이마다 의미 있는 시험인지 함께 봐야 한다.

## 9. 한계와 열린 항목

- 시험은 코드가 모델의 **규칙**대로 움직임을 보인 것이고, 규칙 자체가 현실의 스케줄러를 닮았는지는 별개다(모델 타당성은 선행연구 위치 잡기와 사전 분석 계획에서 다룬다).
- 사례 14개와 불변식은 모델의 모든 경로를 덮지 않는다. 변이 점검은 36가지 변이에 대한 것이다.
- CPU별 실행 기록(틱 추적)으로 "같은 틱에 한 task를 두 CPU가 실행하지 않음"을 직접 검사하지 않고 항등식과 사례로 간접 확인한다. F1의 정지 0 사건 수는 `sim.py` 사본에 한 줄을 더해 센다(`analysis/diag_f1.py`).
- 신뢰구간은 seed 10개의 탐색용이다. 확인용 실행의 통계 계획은 사전 분석 계획 초안에서 따로 정한다.
- **사람이 정할 일**: F1 보정 모델을 기본으로 삼을지(§4.5).
